# Persistent board models on D1 (#2 follow-up)

Boards, members, categories, cards and votes are stored in D1 and reached through
`remix/data-table`'s `Database`, built around our own D1 `DatabaseDriver`
(see `0002-d1-access.md`). The in-memory demo store no longer exists in production code.

```text
Worker fetch -> openDatabase(env.DB) -> loadAppDependencies (context.db)
  -> loadBoardModels: createDbBoardModels(db, viewerFromSession)
  -> controllers call context.models (the BoardModels interface)
  -> model functions own queries and rules, taking a Database
```

## Layout

- `database/migrations/000N_*.sql`: the physical schema. Wrangler tracks applied files;
  tests replay the same files into an in-memory SQLite database (`app/test/db.ts`).
  Migrations were edited in place while the database was local only. From the first
  remote apply on, an applied migration is never edited: add a numbered file.
- `app/data/tables.ts`: `table()` declarations mirroring the SQL. Nothing checks the two
  agree except the model tests, so every column is exercised by one. Enums use
  `as const` (otherwise `enum()` widens to `string`). Booleans are `integer()` 0/1
  because our D1 driver converts `boolean()` columns on read and the SQLite test driver
  does not; the read models convert.
- `app/data/board.ts`: the application's `Board`, `Category`, `Member`, `Card` shapes.
  Rows are snake_case; `models/boards/load.ts` and `models/cards/card.ts` are the places
  that convert.
- `app/data/limits.ts`: every length and rate limit, shared by schemas, tables and tests.
  The SQL `CHECK` constants are copies and say so in comments.
- `app/models/`: model functions grouped by subject, each test beside its file, no barrel
  files (import the specific module):

  ```text
  board-models.ts        the BoardModels interface controllers depend on
  db-board-models.ts     implements it by delegating to the functions below
  boards/    board.ts (rows) · load.ts (Board shape) · state.ts (status, voting)
             create.ts (the 3-step flow) · section.ts (active section)
  members/   member.ts
  categories/ category.ts
  cards/     card.ts (cards, rate limit) · vote.ts · sort.ts · schema.test.ts (table rules)
  ```

  Files that return raw rows (`board.ts`, `member.ts`, `category.ts`) are building blocks;
  `load.ts`, `card.ts`, `vote.ts` and `state.ts` return the app's shapes.

## Consistency without transactions

Our driver rejects transactions, so there are no multi-statement rollbacks. The rules:

1. **Ids are generated by the app** (`crypto.randomUUID()`), so related rows can be built
   before the first write, retries are safe, and board ids in URLs are not guessable.
2. **Write parents first.** Foreign keys make the other order impossible, so the only
   partial states are a parent without children.
3. **Composite foreign keys** `(board_id, x_id)` stop a card or vote mixing boards.
   Deleting a board, category or member cascades; the model refuses to delete a
   category that still has cards.
4. **One statement per invariant.** Closing a board and closing voting is one `UPDATE`,
   backed by `CHECK (status <> 'closed' OR voting_open = 0)`. Categories go in one
   `createMany`.
5. **`createBoard`** writes board, organiser, categories. If a later write fails it deletes
   the board (the cascade removes the rest) and throws `CreateBoardError`. Cleanup is best
   effort: if it also fails, `cleanupFailed`/`orphanedBoardId` are set so the controller
   logs it, and the original failure is always the error reported.
6. **A board is live only with an organiser** (`loadBoard` returns null otherwise), so an
   orphan left by a killed Worker or a failed cleanup is unreachable.
7. **Idempotency is a unique constraint**, not a check: `cards` is unique on
   `(board_id, member_id, submission_id)` and `votes` on `(card_id, member_id)`. A
   collision is resolved by re-reading the winner; any other error is rethrown.
8. **The card rate limit is count-then-insert**, compared in SQL against the database
   clock (the clock that stamps `created_at`). Two truly concurrent requests can exceed
   the limit by a card. This is spam protection, not an invariant; real abuse protection
   belongs in Cloudflare rate limiting rules. Switch to a single conditional
   `INSERT ... SELECT` only if abuse shows it is needed.

Not enforced by the database (model rules): a board has at least one category;
`current_section_id` belongs to the same board.

## Membership and access

A browser is tied to a member by its session (`board-member:<boardId>` -> member id). The
board URL (an unguessable UUID) is the invitation: anyone with it may open the join form,
enter a name and become a participant. Everything else needs that membership.

- **The server is the gate.** `requireBoardMember` runs on every board route (page,
  cards fragment, new/edit/delete note, vote, voting, status). Hiding buttons is only UX.
- **HTML navigations redirect, everything else is 403.** A page GET that is not asking for
  JSON is sent to `/boards/:id/join` (303). Mutations, the cards fragment and anything
  with `Accept: application/json` get 403, JSON for JSON clients, never a redirect, because
  a `fetch` would follow it and read the join page as if it were JSON.
- **`X-Access-Reason: not_member`** is set on every "not a member" 403 so clients can react
  without parsing translated text (the vote button shows the server's message plus a link
  to join). A member being refused for another reason (not the organiser, board closed)
  does not get it.
- **Joining** is one insert (`joinBoard`), refused on a closed board, idempotent per
  session (a repeated submit with the new session redirects instead of adding a second
  member). A person who loses their cookie joins again as a new member and cannot reclaim
  old notes; there are no accounts to recover from. There is no cap on members.
- **Names are unique per board** after normalising: NFKC, case, spacing, zero-width
  characters, Arabic marks/tatweel and alef variants (`members/name-key.ts`). The app computes
  `members.name_key`; `UNIQUE (board_id, name_key)` enforces it, so two simultaneous joins
  cannot both win. `insertMember` is the only writer. A taken name is a 409 with a message and
  the typed value kept; the organiser's name is protected the same way. Known limits: look-alikes
  from different scripts are not merged (hence the **organiser badge** on notes); a person who
  clears cookies cannot rejoin under their old name (no accounts to reclaim it); `name_key`
  is nullable only because SQLite cannot add a NOT NULL column to a populated table and
  rebuilding `members` would cascade-delete cards and votes.
- `app/actions/access.test.ts` is the authorization matrix: every route tried as visitor,
  member of another board, participant and organiser.

## Tests

- Model tests use `createTestDatabase()` and cover constraints, cascades and failure paths.
- `app/test/board-models-contract.ts` runs the same scenarios through the `BoardModels`
  interface against the database implementation and the in-memory test double, so the
  double used by controller tests cannot drift from the real behaviour. Opening voting on
  a closed board is deliberately outside the contract (the real one refuses).
- Controller tests that exercise UI logic still use the double (`app/test/fake-boards.ts`);
  flows through the real router (`router.test.ts`, `locale.test.ts`, new-board) use a
  database, seeded by `app/test/seed.ts` where they need the demo board.

## Not done here

No remote D1 database was created or migrated and nothing was deployed. Applying
migrations with `--remote` and binding the production database are separate, explicit steps.
