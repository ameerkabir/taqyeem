# Guided sessions and durable browser membership

The final candidate was approved for implementation on 2026-11-16 in the #38 implementation conversation. This change evolves the Remix 3 controllers and Worker/D1 app; the design prototype's engine, reviewer presets, identity switches and storage implementation are not application code.

## Compatibility and activation

Migrations 0007–0009 are additive and forward-only. They add category `tone`, `guided_sessions`, `browser_sessions`, membership/evidence revision triggers, and command receipts. They preserve existing boards, member/note IDs, timestamps, anonymity, labels and card votes. No existing board is automatically converted. A `guided_sessions` row is the capability flag; member responses explicitly identify `model: guided-v1`.

New boards get a guided session. A facilitator may explicitly convert an existing board through its Original board model disclosure. Legacy collecting/meeting/closed map to Collect/Discuss/Summary respectively. Conversion preserves old unrestricted card votes as separately labelled historical evidence; it never invents a five-vote historical budget, topic totals, decisions or discussion outcomes. An already closed legacy board has no manufactured closure snapshot. Legacy boards retain their existing controllers until conversion. After conversion, old mutation endpoints reject with 409 and direct writes to legacy progression/votes cannot bypass the guided commands.

New guided sessions require a facilitator category choice before notes or stage commands: use the displayed classic categories or enter 1–8 custom names (one per line, at most 120 characters each). Names must be nonempty and distinct after Unicode normalization and lowercasing. Participants see a waiting state until confirmation. Categories then stay fixed for that session. This is the requested session setup, without a reusable template catalogue or later category-management interface.

Migration 0010 adds this pending setup state to existing empty Collect sessions, leaving populated sessions, later stages and boards without a guided-session record unchanged. It does not replace any categories during migration. Confirmation uses the same versioned, facilitator-only command boundary; SQLite triggers replace the empty category set and persist its tones within that one atomic update, alongside the command receipt. A separate insert trigger rejects notes while setup is pending. Competing choices cannot partially replace categories or overwrite the winning choice; identical retries return the committed result. Existing notes and category IDs on populated boards are preserved.

Category tone is assigned once from original position modulo four during migration and on category insertion. Rendering reads that stored key, independently of locale, sort order or shelf. Future category-management commands must preserve it and participate in revision control. Colour never establishes authority or ownership.

## One atomic statement per command

D1's existing adapter does not support transactions. Shared session state is an aggregate JSON record with an integer revision. The server reads its revision before reading source evidence, validates the actor against actual board membership and facilitator authority, applies a narrow command, and updates with `WHERE board_id = ? AND revision = ?`. The conditional write also checks current member existence and facilitator role for facilitator-only commands. Evidence and membership changes advance the same revision in database triggers. A competing command either wins or gets an explicit 409; the UI refreshes state, preserves fields and leaves retry to the user. It does not silently replay intent against a different session.

This design puts grouping, allowance, readiness, shared stage, live topic, decisions and proposals in the same consistency boundary. It avoids partially applied multi-row grouping, count-then-insert vote budgets and closure snapshots racing with note edits. Relational notes, members and categories remain their original records. The working aggregate is suitable for the acceptance fixture (50 long notes, 80 members, 20 themes, 30 proposals); it is not an unlimited-size document or a performance/latency guarantee. Larger workloads require measurement and potentially a revised storage layout before expanding supported limits.

A command uses a UUID idempotency key and SHA-256 fingerprint excluding the expected revision. Receipts are separate indexed rows so retries do not grow the working aggregate. An AFTER UPDATE trigger inserts the receipt in the same atomic SQLite statement as the state change; a receipt conflict rolls back that statement. A retry by the same actor with identical intent returns current state without another mutation, including after a lost response. Reusing a key for changed intent or another actor fails. Receipts persist with their board; no expiry silently re-enables old commands. A compatibility migration preserves receipts from the pre-release local iteration. Successful commands are limited to 60 per member/minute; idempotent retries are checked first. Existing note length, ownership, submission-id idempotency and rate limits remain in place.

The default topic allowance is five; the facilitator can set 1–20 in Collect/Group. Topics are themes plus ungrouped notes. One member can select a topic once, remove it to restore allowance, and independently signal readiness. Closing freezes the ballot; reopening retains choices and advances its generation so old pending commands cannot reappear. Aggregates and other members' selections never enter a browser response before closure. Even afterwards, individual ballots stay private. Ties and zero-vote topics follow original source order (`created_at`, then stable note ID), independently of translated labels and vote arrival order. Grouping is optional and only available in Group; no active ballot can be regrouped.

In Group, a facilitator selects ungrouped notes and either creates a named theme or uses **Add selected notes** on an existing theme. Appending retains the original theme ID/title and the source note records. Notes can belong to only one theme; empty, repeated, already-grouped and foreign-board note selections are rejected. Create and rename enforce board-scoped unique theme names after Unicode NFKC normalization, removal of invisible formatting characters, collapsed whitespace and lowercasing. Rejections preserve input, competing commands use the same revision guard, and identical retries do not duplicate membership. Existing duplicate themes are not automatically merged or deleted; their identities and evidence remain intact and facilitators can rename them during Group. Native submit buttons carry the chosen theme without requiring a new title; the browser enhancement preserves that submitter value before disabling pending controls.

Only facilitators advance the six stages. Leaving Vote requires explicit closure. Navigation does not imply discussion: shared live topic, viewer-private topic, explicit discussed/skipped outcomes and decisions are separate. Missing outcomes mean unaddressed. A decision can record why no action is needed. Participant proposals start suggested; facilitator proposals start agreed. Suggested/agreed/deferred/declined disposition is distinct from agreed-action open/completed progress. Authors can edit their own unresolved suggestions; facilitators can edit before closure. Owners are actual joined members, with searchable entry. Destructive proposal deletion is intentionally replaced by retained disposition, following the final #22 contract.

## Immutable agreement and later progress

Actions → Summary writes one closure snapshot containing original evidence/category keys, ordered topics, actual outcomes, decisions and every proposal, including unresolved/deferred/declined ones. A database trigger prevents rewriting or removing that snapshot and prevents leaving Summary after closure. Later completion is allowed only to the current facilitator or assigned owner of an agreed action; it changes current progress and timestamp, not historical agreement. Historical and current progress are displayed separately. Copy/print uses the recorded evidence; print expands all source disclosures and restores the viewer's reading state afterwards.

## Durable identity and viewer state

Remix session middleware now uses D1 storage with an opaque, signed HttpOnly/SameSite=Lax cookie. Middleware adds Secure on HTTPS; backend expiry and cookie expiry are both enforced at 30 days. Unknown or expired IDs are never reused. Regeneration preserves memberships across boards, deletes the old session ID, and new storage/router instances read the same rows. The session loader accepts a signing-key ring for planned rotation (first key signs, remaining keys verify). The current Worker binding still supplies SESSION_SECRET; keep it stable across restarts and define the deployment's rotation/retention policy before release.

The old module-memory session contents cannot be reconstructed from D1 member names. Existing cookies whose backing memory has already disappeared cannot recover ownership; a lost or expired cookie cannot reclaim an identity or facilitator role by name. Cross-device recovery and accounts are not promised. Old in-flight application sessions require a deliberate release window; migrating to durable storage does not retroactively recover a lost isolate. Membership/role authorization is rechecked on every request and command.

Appearance and language preferences are separate from identity. Appearance has a native POST/cookie fallback and a browser enhancement; language uses the existing native form. Native note/edit forms preserve rejected values. Browser note/action/decision/grouping drafts, focus, selection and private navigation are per tab/member/board. They are not a shared state store or cross-device recovery. Storage failure keeps mounted inputs but cannot promise recovery after closing a tab. The workspace is keyed by board and member, preventing another board from inheriting its state. Anonymous authorship is stripped from hydrated payloads and historical snapshots for other viewers; legacy vote counters receive only the note ID, board ID and aggregate, not authorship.

## Transport and failure recovery

Visible working pages poll the authenticated session endpoint every 2.5 seconds and refresh on reconnect. Viewer-scoped ETags return 304 for unchanged revisions. The endpoint is private/no-store; membership changes and note edits advance revisions. Responses cannot overwrite a newer local response. Polling does not replace active editors or change deliberate private reading. There is no online-presence count or availability/realtime latency claim. Lost authorization presents a join link while retaining the mounted draft. Pending, saved, rejected and interrupted states reflect actual requests. Storage errors preserve native POST fields for retry; unsafe or stale commands are never treated as success.

## Rollout and recovery

No remote migration, deployment or production conversion is part of this branch. Before release, back up D1, validate the additive migrations against a populated copy, preserve the signing secret, schedule an old-client/session transition window, apply numbered migrations, then deploy matching code. Existing boards remain legacy until explicit conversion. Old memory-only session mappings cannot be reconstructed from opaque signed cookie IDs after their isolate is gone; D1 prevents future loss but cannot retroactively restore those mappings. Resolve the existing facilitator/session transition before release rather than promising recovery by name. A deployment must not enable new code before its tables/triggers exist. Prefer a forward fix for guided boards; rolling back to old code after activation would let old endpoints misunderstand new stage policy, so do not remove the guards or delete guided records to make rollback appear successful. Restore a verified backup only under a separately planned recovery procedure.

Release acceptance still needs native Arabic review, real iOS/Android keyboards, screen readers, Safari/Firefox, zoom/text spacing, real clipboard/PDF pagination, cross-device and long-session/pilot checks. Chromium automation and local D1 are evidence of the checked paths, not WCAG certification or production release approval. See `docs/design/implementation/VERIFICATION.md` for exact checks and reproducible commands.
